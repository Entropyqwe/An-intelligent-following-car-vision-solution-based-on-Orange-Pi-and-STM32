## 实测结果与正确解释

| 场景 | 结果 | 说明 |
| --- | --- | --- |
| 初始 NPU 人体单项，狗图片无人 | 平均约 88.46ms | 包含最初低效输出拷贝 |
| 优化完整输出拷贝后，同一基准 | 约 38.84ms | 不是完整跟踪 FPS |
| 紧凑候选后，同一基准 | 约 31.24ms | 预处理5.68ms，NPU与输出25.56ms，空候选后处理约0.005ms |
| 真实相机流程的人体处理 | 约32～36ms | 已真实运行模型 |
| 真实相机单独采集，明亮画面 | 预热后约33.3FPS | 实际属性返回60，但不能拿60当实际帧率 |
| 有脸、持续身份核验，无窗口 | 多数约20～23FPS | 未稳定24；人脸核验平均约45～53ms |
| 有脸、完整遥测窗口、未有效锁定 | 多数约16～17FPS | CPU核验和显示均有耗时 |
| 核验较少或画面无清晰人脸的窗口 | 约24～25FPS | valid=0%，不能当稳定锁定验收 |
| 稳定锁定 + UI + 真串口 | 待测 | 用户已报告锁定，但 SSH 在读取前失联 |

真实阳性图片上，threshold=0.25 时得到 1 个人体，紧凑解码框约 `(119.999,131.270,321.940,341.401)`、confidence≈0.288529；与完整解码逐项比较通过（坐标误差小于0.001）。这证明正例解码一致，不证明任意光照、姿态下的召回率。主程序默认 threshold=0.45，不能为了帧率数字而静默改变阈值或放宽原身份冲突规则。

SFace 单脸在固定图片上的 CPU 推理约32～36ms，另有 YuNet、对齐和 UI 等开销。不同线程数有波动：2线程人脸全流程约44.6ms、8线程约40.5ms，但实际 GUI 下未证明8线程必然更快。

## 本次调整过的板端状态

- 相机 `exposure_dynamic_framerate`：1 → 0，避免自动曝光主动降低输出率。
- CPU governor：原 `ondemand` → 临时 `performance`；SFace 耗时没有明显改善，不能把此设置宣传成必选加速。
- NPU governor 原本已是 performance / 1008000000Hz，没有超频。
- 未安装开机自动视觉控制服务。
- 未安装新的系统 NPU SDK、未替换驱动、未改原 Python 虚拟环境。
