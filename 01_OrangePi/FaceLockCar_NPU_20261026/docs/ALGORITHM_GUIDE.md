# FaceLockCar 人脸识别与人体连续跟随实现原理

日期：2026 年 10 月 23 日。

本文面向需要阅读、调试和移植 FaceLockCar 的开发者，解释原有人脸算法、此次人体扩展、输出协议及香橙派验证方法。新版保留人脸模式，通过 `--body` 开启人体扩展。总体方案为 YuNet 人脸检测、SFace 身份识别、NanoDet 人体检测和基于相邻帧几何关系的目标关联。

先给出能力边界：**系统先看到正脸并确认登记身份，才能建立该身份与人体的绑定；之后在人体检测连续且没有关联歧义时，允许目标转身。人体一旦漏检、混淆或离开画面，就停止输出有效目标，等待再次认脸。** 这不等于从任意背影重新识别特定身份，当前没有人体 ReID 模型，也没有永久人体身份库。

## 1 原版算法如何工作

### 1.1 相机采集与处理线程

`main.py` 的 `LatestCamera` 调用 OpenCV VideoCapture 打开摄像头。Windows 使用 DirectShow，Linux 使用 V4L2。请求 MJPG、640×480、30 FPS 和单帧缓冲；这些是请求值，驱动不一定全部接受。

采集线程不断读取图像，只保存最新一帧、收到该帧时的 `time.monotonic()` 和递增帧序号。主循环只处理新序号，不遍历堆积的旧帧。主循环拿到的是图像副本，避免线程间同时修改。这样设计是为了控制延迟：推理慢时主动舍弃中间帧。

`captured` 是电脑收到帧的时间，不是摄像头曝光时间。因而程序统计的帧龄不包含未知的传感器和驱动内部延迟。

### 1.2 YuNet 找到人脸

`vision.py` 使用固定模型 `face_detection_yunet_2023mar.onnx`。输入帧先缩放为 320×320，再由 YuNet 输出人脸框、五个关键点及检测置信度。程序把坐标和关键点按横纵比例分别还原到原图，最多处理面积最大的五张脸。原图中宽或高小于 45 像素的脸不进入身份识别。

YuNet 回答的是“哪里有脸”，不会回答“这是谁”。检测阈值 0.85 与 NMS 阈值 0.3 是当前工程参数。320×320 的缩放没有保持宽高比；恢复坐标能还原位置，但缩放产生的形变仍可能影响检测质量。这是原有实现的取舍，可在后续针对实际镜头比较保持比例的预处理。

### 1.3 SFace 将脸转为特征

程序用 `FaceRecognizerSF.alignCrop` 根据五个关键点对齐人脸，尽量让眼睛、鼻子和嘴处于统一位置，再用 `face_recognition_sface_2021dec.onnx` 提取特征。特征向量经 L2 归一化，得到长度为 1 的向量。当前模型输出为 128 维，但匹配代码本身没有把长度写死。

这一步没有训练新神经网络。用户按 N 进行的“登记”只是采集并保存特征样本，不会修改 SFace 的模型权重。

### 1.4 登记和编号库

按 N 时要求画面里恰好有一个满足识别条件的人脸。采样要求脸框至少约 70×70 像素，相邻样本间隔至少 0.2 秒，共采集 8 个样本。后续样本与首个样本的余弦相似度若低于 0.40，登记取消。

`Gallery.add` 为新人分配递增正整数 ID；已认出的 ID 可补充样本。每个 ID 最多保留最近 30 个样本，写入 `data/gallery.json`。保存使用临时文件再替换的方式，降低写到一半留下损坏 JSON 的机会。编号库记录 schema 和特征模型版本，避免混用不兼容格式。

编号 0 表示没有识别出身份。登记是显式操作，不会自动把路人加入库。移植设备时应一起复制 `data/gallery.json`，否则原编号不会保留。

### 1.5 身份匹配计算

`core.py` 的 `Gallery.match` 用归一化特征的点积计算余弦相似度：

```text
query = feature / ||feature||
score(ID i) = max(query · sample)，sample 遍历该 ID 保存的样本
best = 得分最高的 ID
accept = best_score >= 0.45 且 best_score - second_score >= 0.05
```

0.45 是默认相似度门限，0.05 是最高分与次高分的最小差距，可通过 `--similarity`、`--margin` 调整。余弦相似度不是识别概率；0.80 不能直接解释为 80% 准确率。多样本取最大值有利于覆盖姿态变化，也需要用实际人员测试误认风险。

一帧中如果两张脸都声称是同一个 ID，`unique_identities` 将这两张脸都置为未知，避免直接用其中一张作为控制目标。

### 1.6 原版目标锁定

用户点击人脸、按 1 到 9，或用 `--target ID` 选择目标。`TargetLock` 只接受所选 ID，必须连续确认 3 个处理帧才有效。目标缺失或出现重复候选立即输出无效；时间间隔超过 0.5 秒也会重新累计确认。目标离开时保留选中的 ID，不会自动改跟最大脸或最近的人。

原版每个处理帧都依赖正脸特征。人转身后通常不再有可识别的正脸，所以失去有效目标是其原有行为。

## 2 新版的人脸和人体如何协作

### 2.1 执行流程

```text
最新相机帧
  ├─ YuNet → 人脸对齐 → SFace → 登记身份匹配
  └─ NanoDet Plus → person 检测框
                  ↓
          把指定人脸关联到唯一人体
                  ↓
          连续 3 帧身份和人体确认
                  ↓
          正脸可见 FACE / 连续背影 BODY
                  ↓
          漏检或歧义 LOST → 停止 → 重新认脸
```

`--body` 开启新版。人体每个处理帧都检测一次。尚未锁定、正在登记或正在重新寻找目标时，每帧检查人脸；人体已锁定时默认每 3 个处理帧检查一次人脸，通过 `--face-every` 配置。它表示处理帧间隔，不是相机采集帧间隔，也不是固定秒数。处理越慢，身份复查的时间间隔越长。

界面显示最近一次检查的人脸框，便于点击；关联和控制只使用本轮实际检查结果，不把旧人脸框当作本轮身份证据。

### 2.2 为什么选 NanoDet Plus

新增的 `body_vision.py` 使用 OpenCV Zoo 固定提交里的 `object_detection_nanodet_2022nov.onnx`。这个模型以 OpenCV DNN 在 CPU 上推理，模型文件约 3.80 MB，不增加 PyTorch、Ultralytics 或新的推理运行时依赖。文件大小不代表内存占用，板上实际峰值内存需要另外测量。

NanoDet 是轻量单阶段目标检测器。当前模型输出 COCO 类别，本工程只保留最大类别为 person 且分数达到门限的候选。**只保留 person 是后处理过滤，模型仍执行原来的多类别网络计算。** 检测器能处理不同朝向的人体，但没有“任何背影必定检测成功”的保证，远距离、遮挡、模糊和画面截断都会影响结果。

### 2.3 人体图像预处理与框解码

原图按比例缩放到 416×416 的范围，用黑色填充剩余区域，避免把人拉宽或压扁。图像从 BGR 转为 RGB，按官方示例的均值和标准差归一化，转成 NCHW 输入。

固定 2022nov 模型实际输出三个特征尺度，步长分别为 8、16、32，共六个张量：三个分类张量和三个边框回归张量。每条边用 8 个离散值表示距离分布，经稳定 softmax 后求期望，再乘该层步长，得到相对网格点的左右上下距离。

解码后减掉填充偏移，按实际缩放比例恢复原图坐标，并裁剪到图像边界。过小人体框被过滤，再用 NMS 去除明显重复候选。默认人体门限 0.45，NMS IoU 门限 0.5。阈值是原型参数，不是针对用户现场标定后的准确率保证。

### 2.4 身份如何绑定到人体

`body_tracker.py` 中的 `BodyTargetLock` 负责绑定。绑定要求目标已是所选登记 ID，且人脸至少 80% 的面积落在人体框内；人脸中心位于人体横向范围及上方 65% 高度区域。满足条件的人体必须唯一。

绑定后连续三帧确认才能输出有效目标。人体框与其他检测人体有明显重叠时，放弃绑定。人体内部存在多张脸、其他已登记身份或检查得到的未知脸时，也放弃绑定。这些规则会导致部分侧脸、拥挤或近距离场景更容易停止，是当前保守策略的代价。

### 2.5 转身后如何继续

已经锁定的目标没有正脸时，对比上一帧人体框与本帧人体框。候选必须同时满足以下条件：

| 条件 | 当前门限 | 含义 |
| --- | --- | --- |
| 相邻帧时间差 | 大于 0 且不超过 0.5 秒 | 太久没有更新时，不延续旧绑定 |
| 框 IoU | 至少 0.25 | 新旧人体位置仍有足够重叠 |
| 面积比 | 0.5 至 2.0 | 防止突然换成体积差很多的框 |
| 归一化中心位移 | 不超过 0.6 | 位移按旧框宽高归一化后计算 |
| 合格候选数 | 恰好 1 个 | 多个候选时不猜测 |
| 与其他人体交叠 | IoU 不超过 0.15，且交集不超过较小框面积的 25% | 发现交叉混淆时停止 |

满足这些条件时，系统输出 BODY，表示“同一个已绑定人体的连续轨迹假设”。当前帧的人脸相似度不再有效，因此输出 sim=-1000，并用 source=2 明确标记。

当前实现没有卡尔曼滤波、光流、服装特征或人体 ReID，也没有采用 ByteTrack 或 BoT-SORT。它依赖检测框的空间连续性，适合先验证低速、画面较简单的原型。相机快速转动、人体框跳动或多人靠近时，可能频繁停止。没有被检测出来的遮挡或行人替换仍可能造成错误延续，几何门限不能证明身份绝对正确。

### 2.6 丢失与重新获取

任何一次人体漏检、候选不唯一、明显交叠、身份冲突、运动不连续或输入过期，都会清空人体绑定并输出 valid=0。**不靠运动预测跨过漏检帧，也不凭一个相似位置的背影重新恢复。** 恢复时必须再次看到所选 ID 的人脸，并连同人体重新完成三帧确认。

正常背影连续链没有人为设置最长秒数，因此只要检测连续且无歧义，就可以持续跟随；相应地，距离上次正脸核验可能越来越久。接收端可根据 F2 的 face_age_ms 设置额外复核期限。

## 3 控制坐标与输出协议

### 3.1 几何含义

```text
cx = (x + w/2) / image_width
cy = (y + h/2) / image_height
ex = (2*cx - 1) * 1000
ey = (2*cy - 1) * 1000
area = w*h / (image_width*image_height) * 1000
```

cx、cy、bw、bh、area 均以千分数输出。ex 为负表示目标在左侧，为正表示在右侧。默认 deadband=120，相当于画面中间约 12% 宽度的区域输出 direction=0；左侧 -1，右侧 1。

原人脸模式使用人脸框。人体模式无论 FACE 还是 BODY，**始终使用人体框**，避免转身时突然切换框的定义。因此人体版 cy、bw、bh、area 与旧版人脸坐标不能直接套用同一套距离或纵向控制参数。area 不是真实距离，单目框面积也没有经过尺度和姿态标定。

### 3.2 F1 与 F2

普通启动保持原 F1。`--body` 使用 F2，并在原字段后追加 source 和 face_age_ms：

```text
F1  @F1,seq,valid,target_id,cx,cy,ex,ey,bw,bh,area,det,sim,direction,age_ms*XX\n
F2  @F2,seq,valid,target_id,cx,cy,ex,ey,bw,bh,area,det,sim,direction,age_ms,source,face_age_ms*XX\n
```

| 字段 | 人体模式的含义 |
| --- | --- |
| valid | 1 表示当前有效且未过期，0 表示停止使用几何数据 |
| target_id | 用户选择的持久化人员编号，丢失时仍保留 |
| det | 人体检测分数乘 1000 |
| sim | 本帧确认人脸时为余弦相似度乘 1000；仅人体延续为 -1000 |
| source | 0 无效，1 本帧人脸核验且人体已绑定，2 仅人体连续关联 |
| age_ms | 当前观测帧的接收帧龄，独立输出线程持续更新 |
| face_age_ms | 距上一次成功核验指定人脸的毫秒数；从未确认时使用 999999 |

校验仍是从 F 到最后一项字段的 ASCII 字节逐个 XOR，输出两位十六进制。发送线程独立以约 10 Hz 运行，每次发送前重新检查帧龄。默认超过 400 ms，valid、source 和几何字段清零；target_id 保留。10 Hz 是心跳，不是模型推理帧率。

**接入电控前，接收端必须支持 F2 版本及人体框语义。** 工程的 `decode_packet` 和 `serial_monitor.py` 已能解析两种版本，但外部单片机代码不会因此自动更新。接收端仍需在 valid=0、通信超时或协议错误时停止使用目标控制位置。

## 4 如何运行

### 4.1 Windows

先退出其他占用摄像头的程序。同一时间只运行一个相机程序。

```powershell
.\.venv\Scripts\python.exe verify_models.py
.\.venv\Scripts\python.exe main.py --camera 1 --body
```

在“运行和调试”中也可选择“4 人脸与人体连续跟随 camera 1”。按 N 登记，点击已登记人脸或按对应数字选择。先正面对镜头完成绑定，看到 FACE 后慢慢转身，观察是否进入 BODY。按 U 解锁，Q 退出。

若已有编号，直接指定：

```powershell
.\.venv\Scripts\python.exe main.py --camera 1 --body --target 1
```

### 4.2 香橙派

先阅读 `DEPLOYMENT_ASSESSMENT.md`。本次方案按用户确认的 Zero 3W A733 评估，但没有获得其内存容量、实际系统和板上性能，因此尚不能给出实测实时性结论。

使用适配本板的 ARM64 Linux，Python 3.10 至 3.12。在板上重建环境，不复制 Windows 的 `.venv`。桌面预览使用 requirements.txt；没有显示服务器的部署使用 requirements-headless.txt，两种 OpenCV 发行包只装其中一种。

```bash
cd ~/FaceLockCar
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
.venv/bin/python verify_models.py
.venv/bin/python camera_check.py --camera 0
.venv/bin/python main.py --camera 0 --body --target 1
```

无界面且已经登记目标时：

```bash
.venv/bin/python main.py --camera 0 --body --no-show --target 1
```

先验证再连接实际串口：

```bash
.venv/bin/python main.py --camera 0 --body --no-show --target 1 --port /dev/ttyUSB0
```

### 4.3 板上性能评估

`benchmark_vision.py` 只运行视觉模型，不发串口控制。建议让真实目标分别正脸、背影、两人同框，每组测量并记录：

```bash
# 查找和重认阶段的较重负载
.venv/bin/python benchmark_vision.py --camera 0 --frames 300 --face-every 1 --output logs/benchmark_acquire.json
# 模拟已锁定阶段的人脸检查频率
.venv/bin/python benchmark_vision.py --camera 0 --frames 300 --face-every 3 --output logs/benchmark_locked.json
```

报告包含平均、P50、P95、最大推理耗时、相机帧龄和超过 400 ms 的比例。compute_fps 只表示模型计算吞吐，不包括绘制、串口、跟踪和完整控制链；静态图测试不能证明实时相机性能。示例图没有检测出人脸时，也无法覆盖多张 SFace 人脸推理的负担。

建议把端到端 P95 明显低于 400 ms、持续 10 分钟没有明显降频或内存问题作为低速原型初筛，再按车速和控制需求设定更严格延迟目标。若通过调大 max-age-ms 才能得到 valid=1，代表允许使用更旧的数据，不代表算法已经加速。

## 5 是否有必要换 YOLO

**现阶段没有必要仅为了背影而把整套算法替换成 YOLO。** 背影问题需要人体检测和身份连续关联，YOLO 只替代其中的检测器；标准 person 模型不能替代登记身份识别。

| 方案 | 能做什么 | 主要代价 | 本工程建议 |
| --- | --- | --- | --- |
| YuNet 加 SFace | 正脸检测和登记身份匹配 | 背影无法核验 | 保留作为身份来源 |
| NanoDet 加现有人脸算法 | 检测人体并延续绑定目标 | 额外推理和几何关联局限 | 当前已经实现，先实测 |
| YOLO nano 加现有人脸算法 | 更换人体检测器，可扩展其他物体类别 | 模型导出、运行时和板上基准需要另行验证 | 作为下一轮对照候选 |
| 仅 YOLO person | 正背面人体类别检测 | 不知道这个人是不是登记目标 | 不满足当前身份需求 |
| 人体 ReID 加跟踪加人脸 | 可加入服装外观特征辅助跨帧关联 | 推理负担、阈值和遮挡重识别复杂度增加 | 当前暂不引入 |

如果后续换 YOLO，推荐先在电脑导出适合 ARM CPU 的格式，再部署推理模型。Ultralytics 官方给 Raspberry Pi 的指南推荐 NCNN，但这不是 A733 的性能保证。不同 YOLO 版本、输入大小、运行时和量化方式必须在同一块板上比较；不能只看模型参数量或网络上的其他板子 FPS。

NPU 也不是安装一个 Python 库就会自动使用。需要与 A733 对应的驱动、用户态 SDK、支持的网络算子、转换及量化工具链。当前工程没有验证这些条件，全部显式运行 CPU。不应把用于 Rockchip 的 RKNN 方案直接当作 A733 的部署方案。

## 6 本次验证结果与限制

本次在 Windows AMD64、Python 3.12.14、OpenCV 4.10.0 环境中完成验证：

- 14 项单元测试通过，覆盖原版身份库、连续确认、坐标和 F1，以及新增的背影绑定、漏检重认、人体交叉、未知脸与身份冲突、时间间隔、F2 和真实人体模型的空场景推理。额外验证了实际输出线程的 F2 心跳、CSV 与退出清零。
- 三个 ONNX 模型通过固定 SHA256 校验。
- 用 Ultralytics 官方 bus.jpg 样例运行真实 NanoDet，默认门限下保留两个 person 框，与相同提交的官方 NanoDet 参考实现一致；还原坐标差异小于 0.5 像素。该样例存在其他未达到门限的人，因此它也说明检测召回仍有限，不能以一次样例代表场景准确率。
- 全黑图像没有检出人体。
- 30 次静态样例图测试，模型流水线平均约 77.6 ms、P95 约 93.6 ms；该样例未检测出可处理的人脸，所以不含实际 SFace 人脸特征计算负担。这是电脑上的有限样例结果，不能推断香橙派 FPS。

尚需在用户现场验证：单人正脸转背影、长时间背影、两人靠近与交叉、遮挡后重新出现、快速转向、相机移动、不同距离和光照、拔相机与串口、实际电控超时行为。单元测试验证状态规则，不能替代真实视频中的漏检、误认和轨迹切换评估。
